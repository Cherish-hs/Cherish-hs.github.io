## 一、什么是 Python 虚拟环境？

Python 虚拟环境（Virtual Environment）是一种为 Python 项目创建独立运行环境的机制。

它可以让不同项目分别管理自己的 Python 第三方依赖，减少软件包版本冲突，避免随意安装依赖影响系统 Python 环境。

例如，我正在学习 Python、OpenCV 和 ROS 2，不同项目可能依赖不同版本的 NumPy。如果所有项目都使用同一套 Python 包，就可能出现依赖冲突。

使用虚拟环境后，可以为不同项目分别安装需要的依赖。

```
Ubuntu
├── 项目 A
│   └── .venv/
│       ├── Python 环境入口
│       └── site-packages/
│           └── NumPy 1.x
│
└── 项目 B
    └── .venv/
        ├── Python 环境入口
        └── site-packages/
            └── NumPy 2.x
```


**核心思想：让不同项目拥有各自的依赖环境，减少相互影响。**

---

## 二、为什么需要虚拟环境？

### 1. 解决依赖版本冲突

假设项目 A 需要：

```
numpy==1.26.4
```

项目 B 需要：

```
numpy==2.0.0
```

如果两个项目共用同一个 Python 包安装位置，就无法同时满足这两个精确版本要求。

使用虚拟环境后，可以分别安装：

- 项目 A：NumPy 1.26.4
    
- 项目 B：NumPy 2.0.0
    

这样两个项目就可以独立管理依赖。

### 2. 避免污染系统 Python

Ubuntu 自身也会使用 Python，部分系统工具依赖特定的 Python 包。

如果随意升级系统级 Python 包，可能导致系统工具出现问题。

因此，开发普通 Python 项目时，尽量将项目依赖安装在虚拟环境中，而不是直接修改系统 Python 环境。

### 3. 方便项目迁移与复现

假设一个 OpenCV 项目在自己的电脑上运行正常，但换一台电脑后，却因为缺少依赖而无法运行。

这时可以通过依赖清单记录项目使用的软件包及版本。

例如：

```
opencv-python==4.10.0.84
numpy==1.26.4
```

保存为 `requirements.txt` 后，其他人可以根据这个清单尝试重建环境。


### 4. 方便测试不同版本

例如，需要比较不同版本的 OpenCV 二维码识别效果，可以创建多个虚拟环境，分别安装不同版本的 OpenCV。

这样就不需要反复修改同一个环境里的软件包。

### 5. 方便清理实验环境

如果一个实验不再需要，可以删除对应的虚拟环境目录，再重新创建。

不过，删除虚拟环境不会自动删除项目源代码、图片、数据集等其他文件。

## 三、为什么虚拟环境文件夹以 `.venv` 开头？

在 Ubuntu 等 Linux 系统中，以英文句点 `.` 开头的文件和目录默认是隐藏的。

例如：

```
opencv_project/
├── main.py
├── requirements.txt
└── .venv/
```

执行：

```
ls
```

通常不会显示 `.venv`。

执行：

```
ls -a
```

则可以看到它。

### 为什么要隐藏虚拟环境？

虚拟环境内部可能包含大量 Python 环境文件、配置文件和第三方依赖。

日常开发时，我们通常更关注：

- Python 源代码
    
- 配置文件
    
- 图片和数据集
    
- 项目文档
    

因此，把虚拟环境命名为 `.venv`，可以让项目目录更整洁，当然你要想命名为 `venv` 或者其他名称随你便。

## 四、虚拟环境的实现原理

Python 官方提供的 `venv` 模块可以创建虚拟环境。

创建命令：

```
python3 -m venv .venv
```

它会在当前目录创建一个虚拟环境目录。

### 1. 虚拟环境目录结构

在 Ubuntu 中，目录结构通常类似：

```
opencv_project/
├── main.py
├── requirements.txt
└── .venv/
    ├── bin/
    │   ├── python
    │   └── pip
    ├── lib/
    │   └── pythonX.Y/
    │       └── site-packages/
    └── pyvenv.cfg
```

各部分的作用如下：

| 文件或目录            | 作用                    |
| ---------------- | --------------------- |
| `bin/python`     | 虚拟环境使用的 Python 解释器入口  |
| `bin/pip`        | 安装和管理 Python 包        |
| `site-packages/` | 保存当前环境安装的第三方包         |
| `pyvenv.cfg`     | 保存基础 Python 安装等环境配置信息 |


### 2. 虚拟环境会复制一份完整的 Python 吗？

通常不会。

虚拟环境会以某个基础 Python 安装为基础创建独立环境，但不一定复制完整的 Python 安装。

可以从三个方面理解。

#### 第一类：解释器入口

虚拟环境中通常会有自己的 Python 解释器入口。

它可能是复制的文件，也可能是指向基础 Python 安装的符号链接等。

#### 第二类：基础 Python 资源

Python 标准库通常继续使用基础 Python 安装中的文件，而不是完整复制一份。

Python 解释器本身也可能依赖系统动态库等资源。

#### 第三类：独立安装的第三方包

例如：

```
python -m pip install opencv-python
```

通常会把 OpenCV 安装到当前虚拟环境的 `site-packages` 目录中。

NumPy、Requests 等第三方包也是如此。

因此，虚拟环境的隔离重点是 Python 包的安装位置和模块搜索路径，而不是复制整个操作系统。

## 五、虚拟环境为什么能隔离 Python 包？

关键是理解：**Python 解释器和 Python 包不是同一个东西。**

例如：

```
import os
import cv2
```

其中：

- `os` 属于 Python 标准库，通常来自基础 Python 安装。
    
- `cv2` 是 OpenCV 的 Python 模块，通常需要在当前环境的第三方包目录中找到。
    

当 Python 执行 `import` 时，会根据模块搜索路径寻找对应的模块。

虚拟环境通过配置自己的搜索路径，使 Python 默认优先使用当前环境安装的第三方包。

因此，不同虚拟环境可以使用不同版本的 OpenCV 或 NumPy，而不必互相覆盖。

### 虚拟环境与系统 Python 的关系

```
flowchart TD
    A[Ubuntu 系统] --> B[基础 Python 安装]
    B --> C[Python 标准库等基础资源]
    B --> D[项目 A 的虚拟环境]
    B --> E[项目 B 的虚拟环境]
    D --> F[项目 A 的 site-packages]
    E --> G[项目 B 的 site-packages]
    F --> H[项目 A 的依赖版本]
    G --> I[项目 B 的依赖版本]
```

需要注意：

- 虚拟环境默认不会把系统级第三方包目录加入自己的常规搜索路径。
    
- 可以通过 `--system-site-packages` 允许访问系统级第三方包。
    
- 虚拟环境仍可能依赖基础 Python 安装和系统动态库。
    
- 虚拟环境不是完全独立的操作系统。

## 六、Ubuntu 创建和使用虚拟环境

下面以 OpenCV 二维码识别项目为例。

### 第一步：安装 `venv`

```
sudo apt update
sudo apt install python3-venv
```

### 第二步：创建项目目录

```
mkdir -p ~/opencv_project
cd ~/opencv_project
```

### 第三步：创建虚拟环境

```
python3 -m venv .venv
```

这时目录中会出现 `.venv` 文件夹。

### 第四步：激活虚拟环境

```
source .venv/bin/activate
```

激活成功后，终端前面通常会出现：

```
(.venv) cherish@ubuntu:~/opencv_project$
```

激活主要是调整当前 Shell 的环境变量，让它优先找到虚拟环境中的 Python 和相关工具。

### 第五步：安装 OpenCV

```
python -m pip install opencv-python
```

这里使用 `python -m pip`，可以更明确地让当前 Python 运行对应的 pip。

安装完成后，检查版本：

```
python -c "import cv2; print(cv2.__version__)"
```

如果成功输出版本号，说明当前 Python 可以导入 OpenCV。

### 第六步：退出虚拟环境

```
deactivate
```

退出后，终端前面的 `(.venv)` 通常会消失。

### 第七步：以后再次使用

```
cd ~/opencv_project
source .venv/bin/activate
```

不需要重新创建环境，也不需要重复安装已经安装的依赖。

## 七、如何验证虚拟环境的工作原理？

### 1. 查看系统 Python

退出虚拟环境后执行：

```
which python3
python3 -c "import sys; print(sys.executable)"
```

Ubuntu 中常见的输出是：

```
/usr/bin/python3
/usr/bin/python3
```

### 2. 查看虚拟环境 Python

激活环境：

```
source ~/opencv_project/.venv/bin/activate
```

然后执行：

```
which python
python -c "import sys; print(sys.executable)"
```

通常会看到类似：

```
/home/cherish/opencv_project/.venv/bin/python
/home/cherish/opencv_project/.venv/bin/python
```

### 3. 查看基础安装和当前环境

```
python -c "import sys; print('解释器:', sys.executable); print('基础安装:', sys.base_prefix); print('当前环境:', sys.prefix)"
```

一般来说：

- `sys.executable`：当前 Python 解释器的路径。
    
- `sys.base_prefix`：基础 Python 安装的位置。
    
- `sys.prefix`：当前 Python 环境的位置。
    

在标准虚拟环境中，`sys.prefix` 通常与 `sys.base_prefix` 不同。

### 4. 查看当前 pip 的位置

```
python -m pip --version
```

通常会显示当前环境中 pip 的安装位置。

### 5. 检查解释器入口

```
ls -l ~/opencv_project/.venv/bin/python
```

如果输出中包含 `->`，说明它是符号链接。

如果没有 `->`，则可能是独立文件。

注意：仅通过这条命令，不能完全判断 Python 解释器的所有底层文件是否共享。

## 八、一个项目可以使用多个虚拟环境吗？

可以。

一个项目可以创建多个虚拟环境，分别用于测试不同版本的依赖。

例如：

```
opencv_project/
├── main.py
├── .venv_old/
└── .venv_new/
```

其中：

- `.venv_old`：安装旧版本 OpenCV。
    
- `.venv_new`：安装新版本 OpenCV。
    

测试旧版本：

```
source .venv_old/bin/activate
python main.py
```

切换到新版本：

```
deactivate
source .venv_new/bin/activate
python main.py
```

这样就能用同一份源代码，分别测试不同环境。

### 能不能同时激活两个虚拟环境？

不能简单地通过连续执行两次 `activate`，就让同一个 Python 进程自动使用两套互相独立的依赖。

原因是：

1. 激活虚拟环境主要修改当前 Shell 的环境变量。
    
2. Python 进程启动后，会拥有自己的模块搜索路径。
    
3. 执行 `import cv2` 时，Python 不会自动根据代码选择不同虚拟环境里的 OpenCV。
    

### 如果确实需要两个环境同时工作呢？

可以将任务拆成两个独立的 Python 进程：

```
flowchart TD
    A[主项目] --> B[Python 进程 A]
    A --> C[Python 进程 B]
    B --> D[虚拟环境 A]
    C --> E[虚拟环境 B]
    D --> F[OpenCV 旧版本]
    E --> G[OpenCV 新版本]
    F --> H[进程间通信]
    G --> H
```

两个进程可以通过 Socket、HTTP、消息队列或文件等方式交换数据。

不过，这种方案会增加通信和维护成本。普通项目通常只需要一个虚拟环境。

## 九、虚拟环境、Docker 和虚拟机的区别

| 对比项         | Python `venv`    | Docker 容器            | 虚拟机            |
| ----------- | ---------------- | -------------------- | -------------- |
| 主要目的        | 隔离 Python 依赖     | 隔离应用运行环境             | 运行独立操作系统       |
| 是否提供独立操作系统  | 否                | 使用容器镜像中的用户空间，共享宿主机内核 | 通常可以           |
| Python 版本管理 | 依赖基础 Python 安装   | 可以在镜像中配置             | 可以安装独立的 Python |
| 系统级依赖隔离     | 有限               | 较强，但仍共享内核等资源         | 通常更完整          |
| 常见用途        | Python 开发、OpenCV | ROS 2、Gazebo、应用部署    | 不同操作系统、系统级测试   |

可以这样理解：

- `venv`：隔离 Python 包。
    
- Docker：隔离应用运行环境及其依赖。
    
- 虚拟机：运行一套独立的操作系统。

## 十、结合 ROS 2 和 OpenCV，应该怎么选择？

如果正在 Ubuntu 上学习 ROS 2、Gazebo、OpenCV，可以根据项目类型选择环境。

| 项目类型              | 建议                            |
| ----------------- | ----------------------------- |
| 普通 Python 算法练习    | 使用 `venv`，也可以使用现有环境           |
| 独立 OpenCV 二维码识别   | 通常使用 `venv`                   |
| ROS 2 Python 节点   | 先确认 ROS 2 的 Python 依赖与虚拟环境兼容性 |
| ROS 2 + Gazebo 仿真 | 可以使用 Docker 管理整个运行环境          |
| iCAN 无人机仿真        | 优先遵循项目提供的 Docker 镜像和依赖配置      |

尤其要注意：ROS 2 的 Python 包、系统动态库和第三方依赖之间可能存在版本要求。

不要假设任意一个新建的虚拟环境都能直接导入 ROS 2 的所有 Python 包。需要根据具体的 ROS 2 发行版和项目配置进行验证。

## 十一、虚拟环境的常见注意事项

### 1. 不要将 `.venv` 上传到 GitHub

通常可以在 `.gitignore` 中添加：

```
.venv/
```

上传源代码、依赖清单和必要的配置文件即可。

### 2. 使用依赖清单

导出当前环境的依赖：

```
python -m pip freeze > requirements.txt
```

在新的虚拟环境中安装：

```
python -m pip install -r requirements.txt
```

`pip freeze` 会记录当前环境中的已安装 Python 包及版本，但不一定能完整描述系统级依赖和所有平台差异。

### 3. 不要随意修改系统 Python 包

普通 Python 项目尽量使用虚拟环境安装第三方依赖。

不要随意使用 `sudo pip install` 修改系统级 Python 环境。

### 4. 激活环境不会自动安装依赖

```
source .venv/bin/activate
```

只是激活环境，不会自动安装 OpenCV、NumPy 等软件包。

### 5. 虚拟环境不等于备份

删除 `.venv` 通常会删除其中安装的依赖，但不会自动删除项目目录中的源代码和数据文件。

### 6. 新开终端通常需要重新激活

激活环境的设置通常只影响当前 Shell 及其启动的子进程。

新开一个终端时，一般需要重新执行激活命令。

---

## 十二、总结

Python 虚拟环境的核心是将不同项目的 Python 依赖隔离开，减少软件包版本冲突，方便项目测试、维护和复现。

需要记住以下几点：

1. `.venv` 以点开头，是为了让环境目录默认隐藏。
    
2. 虚拟环境通常不会复制一整套完整的 Python 安装。
    
3. Python 标准库等基础资源通常继续使用基础 Python 安装中的文件。
    
4. 第三方包默认安装到虚拟环境自己的 `site-packages` 目录。
    
5. 激活虚拟环境主要调整当前 Shell 的环境变量，并不会自动安装软件包。
    
6. 一个项目可以拥有多个虚拟环境，但同一个 Python 进程通常不会自动混用多套环境的依赖。
    
7. `venv` 主要隔离 Python 依赖，而 Docker 和虚拟机提供更广泛的运行环境隔离。
    

**一句话记忆：基础 Python 提供运行基础，虚拟环境管理独立依赖，pip 负责安装 Python 包。**
